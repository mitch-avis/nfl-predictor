# Decisions in the ratings port (roadmap step 6, phase 3)

Every judgment call made while porting `nfl-sos-ratings`' team ratings, preseason prior, schedule
strength, quarterback ratings, weekly histories, rank ranges, and head-to-head pairs into
`src/nfl_predictor/ratings/`, and every place the port departs from that project at its frozen
commit `9081bce`. The port reproduces every published ratings file: the parity report
(`.agents/sos_port/RATINGS_PARITY.md`, generated by `.agents/sos_port/ratings_parity.py`) compares
767,141 cells, all bit-identical except 162 raw season quarterback rates within 1.1e-16. So the
departures below change how inputs are carried, how the code is organized, or what the new
pre-week entry point returns, never a published value.

Commands run from this repository's root with the worktree's environment. "The audit" is
`.venv/bin/python .agents/sos_port/ratings_parity.py`, which writes `RATINGS_PARITY.md` and
`ratings_parity.json` beside it.

## 1. Where the package lives, and where its column names live

- **What differs**: that project keeps the ratings in `nfl_sos_ratings/` (`ridge.py`,
  `team_rating.py`, `team_prior.py`, `qb_rating.py`, `rating_ranges.py`, wired in `main.py`). This
  repository's `AGENTS.md` keeps column names and schema lists in `src/nfl_predictor/constants.py`.
  The port is a new package, `src/nfl_predictor/ratings/`, whose input and output column names
  live in its own modules (`inputs.py`, `team_rating.py`, `qb_rating.py`, `season.py`,
  `pre_week.py`).
- **Options**: (a) a new top-level package with its own column names; (b) the same, with the
  names added to `constants.py`; (c) a module under `src/nfl_predictor/utils/polars/` beside the
  current strength snapshot.
- **Decision**: (a).
- **Reasoning**: `constants.py` is part of every walk-forward checkpoint fingerprint, and
  everything under `utils/` is part of the incremental ETL's season-cache fingerprint. Editing
  either would invalidate every saved fold or force a full ETL rebuild for a change that wires
  nothing into the data or the model. The names become features only when the integration stream
  wires the package in; it can then move the feature-facing names into `constants.py` and add
  `ratings` to the season cache's source directories in the same change that alters feature
  values.
- **Data**: `grep -n '"constants.py", "ml_model.py"' src/nfl_predictor/ml/walk_forward.py` prints
  `646: files.extend(package_dir / name for name in ("constants.py", "ml_model.py"))` (the
  fingerprinted files); `grep -n '^_ETL_SOURCE' src/nfl_predictor/utils/season_cache.py` prints
  `52:_ETL_SOURCES = ("data_collection.py", "constants.py")` and
  `53:_ETL_SOURCE_DIRECTORIES = ("utils",)`. No module outside the package imports it:
  `grep -rln 'nfl_predictor.ratings' src/ | grep -v '^src/nfl_predictor/ratings/'` prints nothing.
- **Feature-value impact**: none; no checkpoint fingerprint or ETL cache key changes.
- **How to reverse it**: move the package or its names; the walk-forward checkpoints and the
  season cache then rebuild.
- **Review**: not yet reviewed.

## 2. The quarterback rows carry the EPA on the dropbacks, not EPA per dropback

- **What differs**: that project's quarterback fit reads the per-game rate `qb_epa_per_dropback`
  from its game logs (`qb_rating.py`, `_REQUIRED_COLUMNS`). The port's quarterback-game rows carry
  `qb_dropbacks` and `qb_dropback_epa`, the EPA on those dropbacks with spikes left out, and the
  fit computes the rate itself (`nfl_predictor.ratings.qb_rating._rated_rows`). The adapter from
  the published logs sets `qb_dropback_epa = qb_passing_epa - qb_spike_epa`.
- **Options**: (a) carry the rate, as that project does; (b) carry the sum and the count.
- **Decision**: (b).
- **Reasoning**: the team rows already carry sums and counts (scrimmage EPA and plays,
  special-teams EPA and plays), and this repository's feature rule is to carry counts and sums and
  compute rates afterward. The rate that project wrote is exactly the passing EPA less the spikes'
  EPA over the dropbacks, so carrying the sum loses nothing and the fits stay bit-identical.
- **Data**: the audit's "Input checks": of 16,281 published passer-games with a dropback, the
  published `qb_epa_per_dropback` equals `(qb_passing_epa - qb_spike_epa) / qb_dropbacks` bit for
  bit in 16,281; none of the 523 passer-games without a dropback carries dropback EPA. Every
  quarterback table the audit compares is bit-identical apart from decision 4's raw season rate.
- **Feature-value impact**: none.
- **How to reverse it**: make `qb_epa_per_dropback` the input column in
  `inputs.QB_GAME_SCHEMA` and drop the division in `qb_rating._rated_rows`.
- **Review**: not yet reviewed.

## 3. Row order: the fits keep the caller's order; the adapter supplies that project's

- **What differs**: nothing in the method. The fits sum over rows in the order given, so the same
  rows in another order can move a rating in its last bits. That project's quarterback fits read a
  season's rows sorted by team, week, game, and passer name, while its published quarterback logs
  are sorted by passer, week, and game; its team fits read the order its team logs are published
  in. The port's functions keep whatever order they receive, and the published-log adapter
  (`published_logs.qb_games_from_published`) re-sorts the quarterback rows to the fits' order.
- **Options**: (a) keep the caller's order and reproduce that project's in the adapter; (b) sort
  inside every fit, so any caller gets the same bits.
- **Decision**: (a).
- **Reasoning**: (a) reproduces the published files bit for bit, bootstrap ranks included, which
  is the strongest check that the port is right; (b) would leave differences near 1e-15 and could
  in principle flip a tied bootstrap rank. The integration stream's adapter should still emit a
  fixed order so its rebuilds are byte-identical; the team order (team, week, game) and the
  quarterback order (team, week, game, passer name) are the natural choices.
- **Data**: with the re-sort removed from the adapter, 8 of the 15 tests in
  `tests/test_ratings_published_parity.py` fail on exact equality (every quarterback table); with
  it, all pass (`.venv/bin/python -m pytest -p no:cacheprovider -n 0 --no-cov
  tests/test_ratings_published_parity.py`). The audit's input checks find 0 passer-game rows tied
  on team, week, game, and name, so the re-sort is unambiguous. The BLAS thread count acts the
  same way: `OPENBLAS_NUM_THREADS=24 OMP_NUM_THREADS=24 MKL_NUM_THREADS=24 POLARS_MAX_THREADS=24
  .venv/bin/python .agents/sos_port/ratings_parity.py --seasons 2024 2026 --out-dir <dir>` passes
  with every team table bit-identical but 3,126 of 55,332 cells only within tolerance (largest
  1.7e-16): 3,124 in the 2024 quarterback tables (fitted ratings, faced pass defense, rating
  percentiles, and pair gaps) and the 2 raw season rates of 2026. With one thread (the audit's
  default, and how that project built its files) only 12 of those cells differ, all raw season
  rates (decision 4).
- **Feature-value impact**: none.
- **How to reverse it**: sort inside `ridge.build_unit_design` and accept tolerance-level parity.
- **Review**: not yet reviewed.

## 4. The quarterback season summary is ported in part, keyed by passer id

- **What differs**: the published quarterback ratings table and rank ranges need each passer's
  season volume (games, dropbacks, attempts), his raw season EPA per dropback, his primary team,
  and whether he qualifies (14 attempts per game of his primary team), which that project computes
  in `qb_stats.compute_qb_season_stats` along with dozens of display statistics. The port
  (`qb_rating.qb_season_summary`) computes only those columns. It groups by passer id, where that
  project groups by id and name, taking the name from the passer's latest game, and it sums the
  per-game dropback EPA where that project subtracts the season's spike EPA total from its passing
  EPA total, so the raw season rate can differ in the last bit.
- **Options**: (a) port the qualifier columns only; (b) port the whole season-statistics module;
  (c) take the qualifier as an input from the caller.
- **Decision**: (a).
- **Reasoning**: the rank ranges and pairs rank only qualified passers, so the qualifier is part
  of reproducing them; the other statistics are display columns outside the ratings and belong to
  the integration stream's statistics work. Grouping by id alone cannot split one passer into two
  rows if a name is spelled two ways.
- **Data**: the audit's input checks find 0 passer ids with two names in a season (1999-2026). The
  audit compares the summary columns in `qb_ratings` and `qb_combined` for every season: every
  cell is bit-identical except `qb_epa_per_dropback`, 162 cells within tolerance, largest
  difference 1.1e-16 (`RATINGS_PARITY.md`, "Cells within tolerance but not bit-identical").
- **Feature-value impact**: none; the raw season rate is a display column.
- **How to reverse it**: group by `["qb_id", "qb_name"]` in `qb_season_summary`; carry
  `qb_passing_epa` and `qb_spike_epa` separately to make the raw rate bit-identical.
- **Review**: not yet reviewed.

## 5. SRS comes from this repository's existing solver

- **What differs**: the published `ratings` table carries `SRS`, from that project's
  `srs.solve_srs`. The port calls this repository's `utils.polars.adjusted_strength.solve_srs`, the
  same method (least squares on point margin, centered, rounded to six decimals), which also drops
  rows with a null margin first.
- **Options**: (a) reuse the existing solver; (b) copy that project's into the package; (c) leave
  `SRS` out of the port.
- **Decision**: (a).
- **Reasoning**: the published table has the column, so leaving it out would leave the table
  unreproduced; a second copy of the same solver would be duplicate code. If the integration
  stream retires `adjusted_strength.py` with the strength snapshot, the import moves with it.
- **Data**: the audit's `ratings` and `combined` rows: every `SRS` cell bit-identical in all 28
  seasons (7,144 and 6,251 cells in those tables, all bit-identical).
- **Feature-value impact**: none.
- **How to reverse it**: copy `srs.solve_srs` into the package and import it in
  `season.build_team_ratings`.
- **Review**: not yet reviewed.

## 6. Pre-week quarterback ratings use the previous season's penalty

- **What differs**: the published quarterback history (`qb_ratings_by_week`) refits each week with
  the penalty cross-validated on the whole season, which is not known before the week. The
  pre-week entry point (`pre_week.RatingsHistory`) fits the passer-games before the week with the
  penalty cross-validated on the whole previous season, as the team fits already do, and refits
  the faced pass defense the same way.
- **Options**: (a) the previous season's penalty; (b) the season's own, as the published history
  does; (c) cross-validate the games before the week.
- **Decision**: (a).
- **Reasoning**: (b) leaks one number chosen from games after the week into every week's feature;
  (c) is unreliable early in a season, where cross-validation sometimes picks the largest penalty
  and rates everyone as average (the reason that project gives for the team fits' previous-season
  penalties). (a) is known before the week and mirrors the team side.
- **Data**: the audit's "Pre-week entry point": the two penalties are equal in 7 of 27 seasons,
  whose pre-week ratings are bit-identical to the published history of the week before; in the
  other 20 the cross-validated choice moved between adjacent grid values (100, 177.8, and 316.2,
  per season in `ratings_parity.json`, `pre_week.qb_penalties`), and the absolute difference in
  adjusted EPA per dropback averages 0.021 over those seasons' passer-weeks (0.015 over all 25,835
  passer-weeks), largest 0.2 (2000 week 15, passer `00-0019553`). Passers, games, and dropbacks
  agree in every week.
- **Feature-value impact**: yes, once the integration stream uses these ratings as features: a
  quarterback's pre-week rating differs from the published history's by the amounts above. Not
  measured as a feature; the integration's walk-forward measures it.
- **How to reverse it**: in `RatingsHistory.qb_penalty`, return the season's own cross-validated
  penalty.
- **Review**: not yet reviewed.

## 7. The pre-week ratings of the first season are null

- **What differs**: the published 1999 ratings cross-validate their own penalties (no earlier
  season exists), so its history uses penalties chosen from the whole 1999 season. The pre-week
  entry point returns null team ratings and no quarterback rows for every week of 1999.
- **Options**: (a) null; (b) 1999's own cross-validated penalties, as the published history; (c)
  a fixed penalty chosen without data.
- **Decision**: (a).
- **Reasoning**: no penalty is known before 1999, and this repository's first rule is no leakage;
  (b) leaks a little, (c) invents a number. 1999 lies outside every evaluation window (they start
  in 2007), and the model handles null features. From 2000 on, every penalty comes from the season
  before.
- **Data**: 1999 has 247 games of 31 teams and 617 passer-games (published 1999 logs); those rows
  get null rating features. The audit's pre-week comparison starts in 2000.
- **Feature-value impact**: yes, once integrated: 1999's rows carry nulls for these features.
- **How to reverse it**: in `RatingsHistory.pre_week_teams` and `qb_penalty`, use the first
  season's own cross-validated fits instead of returning nulls.
- **Review**: not yet reviewed.

## 8. What week 1, a team without a game, and a postseason week return

- **What differs**: that project never rates week 1 (its history starts after week 1's games), and
  it rates a team without a game at that team's prior on the snapshot's scale
  (`team_prior.snapshot_fit`). The pre-week entry point needs a value for week 1. It returns each
  team's full preseason prior, centered over the season's teams, on the previous season's
  league-average scrimmage plays per team-game, with special teams at zero; `sos` null; no
  quarterback rows. Before the first season with a prior (2003) the team ratings are null that
  week. A team without a game in a later week rates at its prior as that project's snapshot does.
  A postseason week returns the fit of the whole regular season.
- **Options**: for week 1, (a) the preseason prior (chosen), (b) null, (c) the previous season's
  final ratings; for quarterbacks in week 1, (d) no rows (chosen) or (e) the previous season's
  rating carried over.
- **Decision**: (a) and (d).
- **Reasoning**: the prior is that project's own answer for a team without games, and the fade is
  1 before any game, so (a) is the same model at zero games; it needs a scale, and the previous
  season's plays per game is the one known before week 1. Centering matches every other week. That
  project has no quarterback prior; carrying a rating over would be a new method that the
  integration stream should measure, not a port. Postseason weeks follow this repository's rule
  that playoff rows use the full regular season.
- **Data**: the scale moves little between seasons: league-average scrimmage plays per team-game
  changed by at most 1.7% from one season to the next in 2003-2026 (mean 0.9%), from the published
  team logs. Week-1 priors exist for 24 seasons (2003-2026). Pinned by
  `test_pre_week_week_one_rates_every_team_at_its_preseason_prior`,
  `test_pre_week_week_one_without_a_prior_has_no_team_ratings`,
  `test_pre_week_team_without_a_game_yet_rates_at_its_prior`, and
  `test_pre_week_postseason_week_fits_the_whole_regular_season` in
  `tests/test_ratings_pre_week.py`.
- **Feature-value impact**: yes, once integrated: these are the week-1 values of the rating
  features.
- **How to reverse it**: in `RatingsHistory.pre_week_teams`, return null ratings when no game has
  been played (drop the `_preseason_ratings` branch).
- **Review**: not yet reviewed.

## 9. A team without a previous season raises in a season with a prior

- **What differs**: that project's `prior_means` raises when a team in the fit has no
  previous-season effect. The pre-week entry point keeps that: in a season with a prior (2003 on),
  a team in the caller's list or the games that did not play the season before raises a
  `ValueError` naming it.
- **Options**: (a) raise; (b) rate such a team at a zero prior; (c) leave it null.
- **Decision**: (a).
- **Reasoning**: from 2003 every team played the season before (Houston joined in 2002), so the
  likely cause is a team-code mismatch in an adapter, which should fail loudly rather than become
  silent nulls or zeros. A real expansion team would need a decision about its prior anyway.
- **Data**: the published logs hold the same 32 teams in every season from 2002; pinned by
  `test_pre_week_team_without_a_previous_season_raises_in_a_prior_season`.
- **Feature-value impact**: none today.
- **How to reverse it**: give such teams a zero raw prior in `team_prior.prior_means` (that
  project's function, so a departure from it).
- **Review**: not yet reviewed.

## 10. What the parity checks compare, and the tolerance

- **What differs**: nothing in the port; these are choices about how parity is judged.
- **Options**: exact equality everywhere, or a stated float tolerance with the bit-identical cells
  counted separately.
- **Decision**: integers, ranks, text, and flags must be equal, and the columns, types, and row
  keys must follow the published order; floats must agree within 1e-12 absolute, and the report
  counts the bit-identical cells. The audit compares every season's `ratings`, `team_prior`,
  `ratings_by_week`, `rating_ranges`, `rating_pairs`, `qb_ratings`, `qb_ratings_by_week`,
  `qb_rating_ranges`, and `qb_rating_pairs`, the 2026 weekly rank ranges, the rating columns of
  `combined`, and the passer columns of `qb_combined`; 2026 is compared in full, not only its
  weekly ranges, because it is the one season whose own fit and `sos` carry a prior. The tests
  under `tests/` expect exact equality on their fixtures, with 1e-15 for the raw season rate.
- **Reasoning**: a tolerance keeps the check meaningful if a library update moves a last bit, and
  the bit-identical count shows how much stronger the result actually is. The rest of `combined`
  and `qb_combined` are season statistics outside the ratings.
- **Data**: the audit: 310 tables, 767,141 cells, 766,979 bit-identical, 162 within tolerance, 0
  outside, 0 structural differences.
- **Feature-value impact**: none.
- **How to reverse it**: set `FLOAT_TOLERANCE = 0.0` in the audit (it then fails on the 162 raw
  season rates).
- **Review**: not yet reviewed.

## 11. The test fixtures are Parquet, with one ignore-rule exception

- **What differs**: this repository's `.gitignore` ignores every `*.parquet`, and its other test
  fixtures are CSV or JSON. The ratings fixtures (`tests/fixtures/sos_ratings_parity/`) are
  Parquet, and one line in `.gitignore` re-includes that directory's Parquet files.
- **Options**: (a) Parquet with the exception; (b) CSV, with the rank-probability lists as text;
  (c) NDJSON.
- **Decision**: (a).
- **Reasoning**: Parquet keeps every type and float exactly as published (the full-file cuts have
  the same SHA-256 as their sources), holds the list column natively, and is about half the size.
  The generator, `.agents/sos_port/ratings_fixtures.py`, rewrites the files byte for byte, and
  `manifest.json` and `PROVENANCE.md` beside them record each source file, the cut, and both
  hashes, which a test checks.
- **Data**: the 21 fixtures take 238,369 bytes as Parquet and 462,065 as CSV (measured with
  `.venv/bin/python -c` reading each fixture and writing it to CSV in memory, lists joined with
  `;`). Two runs of the generator give an identical `manifest.json`.
- **Feature-value impact**: none.
- **How to reverse it**: write CSV in the generator, drop the `.gitignore` line, and read CSV in
  the tests with the published schemas.
- **Review**: not yet reviewed.
