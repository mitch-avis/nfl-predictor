- **Is it the right condition?** Yes. With no strength column, leaving out `strength` removes
  nothing, so the default change does no harm there, and `''` would train on exactly the same
  columns. The check exists to catch the regression the new default creates, and that regression
  needs strength columns to be dropped.

  existed. Every build since the port carries both groups. `finalize.select_final_columns` adds
  every expected column as nulls (`utils/polars/finalize.py:139-142`), and the expected list
  includes both `ADJUSTED_STRENGTH_STATS` and `RATINGS_FEATURE_STATS` (`finalize.py:64,68`).
  Builds between the strength family and the port, today's `data/completed_games_ml.csv` among
  them, have strength and no ratings, which is exactly the case the check catches. The season
  cache keys on the code hash (`utils/season_cache.py`), so an incremental refresh cannot mix
  cached pre-port seasons without ratings columns into a new build.
- **Does any production path still train on neither without a message?** Not through missing
  columns.
  - `train`, and the web train job (a CLI subprocess, `catalog.py:222`), stop.
  - The weekly run, and the web weekly job (`catalog.py:197`), stop in stage 1. A reused stage 1
    either goes through `write_reused_predictions_source` (stops) or reaches the final fit
    (stops).
  - `backtest` and the web walk-forward warn, as the contract asks.
  - The remaining gap is a build whose ratings columns exist but are all null. That happens when
    the ETL has no play-by-play (`utils/polars/ratings_build.py:239-243`, which logs a warning at
    build time). The presence check passes, and my test shows `train` fits without a message
    (P3-C).
- **Does it fire before expensive work?** In `train`, it runs right after the CSV loads and
  before any fit. In the weekly run, it runs after the data refresh, as it must, because the
  refresh produces the columns. Two cheap steps come before it: `_start_run` and the reference
  pool load (`weekly_run/pipeline.py:671-688`). It always runs before the first fold. It does not

### P3-B: two README group pointers read as recipes

README.md:1472 `(--disable-feature-groups ratings; ...)` and README.md:1533

### P3-C: ratings columns that are all null pass the check

The check is presence-only (`ml/feature_spec.py:234`). A current build without play-by-play
keeps all-null ratings columns, so a default `train` fits on neither group with no message. My

warns at build time, so this is low priority. Fix (optional): in the `train` and weekly callers,
which hold the DataFrame, treat ratings columns that are all null as missing.

### P3-D: the weekly check runs late and skips `--dry-run`

The check fires inside stage 1 (`weekly_run/stage1.py:184`), after `_start_run` has created the
run directory and after the reference pool loads (`weekly_run/pipeline.py:671-688`). A
`--dry-run --skip-data-refresh` on old data reports success. Nothing expensive runs first, so
this is optional. Fix: run the check once in `pipeline.main` after the refresh, from the CSV
header.

### P3-E: `home_win_prob` now accepts a numeric string

`np.asarray(sigma, dtype=float)` (`ml/floor_sigma.py:127`) parses `"13.5"` as 13.5, where
`math.isfinite` used to raise `TypeError`. No caller passes a string. Fix (optional): refuse
`str` and `bytes`, or check `np.issubdtype(np.asarray(sigma).dtype, np.number)` before
converting. My test `test_a_string_sigma_is_refused` fails. Related commit-hygiene nit: `ac035e6`
changes help text and its snapshot in one commit, not test-first.

The two failures:

- `test_train_stops_or_warns_when_the_ratings_columns_are_all_null` (P3-C);
- `test_a_string_sigma_is_refused` (P3-E).

What passes:

- **The ratings check:** it stops when only `strength` is left out, and when `strength` and
  `ratings` are both left out on old data. It stays quiet for that same ablation on new data. One
  `ratings_*` column is enough to pass. Lookalike names such as `home_power_rating` do not count.
- **The null key:** the empty YAML key, `~`, and a key whose items are all commented out are each
  refused with "has no value". `[]` still means no group, and a JSON `null` is refused. A null key
  is refused even when the command line names groups. A null list item is refused.
- **The sigma:** an empty array, a two-element list, tuple, Series or 2-D array each raise
  `ValueError`. A one-element Series, array, 2-D array or list, and `float32`, each give the
  float's floor. A negative Series, an all-NaN array, an infinite list and `None` each raise
  "finite and positive". A bad vector names the finite rule before the count rule.

The code that fails:
