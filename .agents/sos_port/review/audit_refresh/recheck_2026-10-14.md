## 5. Findings

### P2

- **`gl-faced` is a rule-10 gap of the same kind as the one fixed**
  (`.agents/sos_port/mapping.yaml:585-592`).
  - It classes `attempts_faced` and `completions_allowed` as `matched`, and its note says "the
    opponent's row".
  - Its counterparts name own-row columns (`box_score:pass_attempts`,
    `box_score:pass_completions`), and no parity pair judges them: `PARITY.md` lists both with
    "-" under pairs.
  - The judgment is true. `recheck_faced_check.py` (read-only, on the published game logs) finds
    0 of 13,928 team-games where either column differs from the opponent's `attempts` or
    `completions`. Together with the existing own-row `pass_attempts` and `pass_completions` pairs
    (0 mismatched), that shows equality, but only by transitivity in my script, not in checked-in
    output.
  - **Fix:** add two `row: opponent` pairs to `parity.yaml` (`pass_attempts` against
    `attempts_faced`, `pass_completions` against `completions_allowed`) and switch the
    counterparts to `box_score[opponent]:...`. That costs about 2 minutes of rerun.

### P3

- **The opponent-row marker is missing from the `different` rules that describe the opponent's
  row.**
  - `gl-official-allowed` (`mapping.yaml:569-584`, 10 columns), `gl-first-downs-allowed`
    (`:626-631`) and `gl-receiving-allowed` (`:657-664`) say "the opponent's row" but name own-row
    counterparts.
  - They claim no equality, so there is no rule-10 gap, only an inaccurate pointer of the kind the
    first review flagged for `gl-carries-faced`. The task calls this rule `gl-defense-allowed`;
    there is no rule by that name, and the closest is `gl-official-allowed`.
  - **Fix:** add `[opponent]` to the `box_score:` counterparts. The `team_stats:` ones would need
    the marker on that catalog too.
- **An opponent-row pair drops a team-game silently when the opponent row is missing**
  (`parity.py:269-273`, inner join).
  - The run still fails through `check_keys`, which records the one-sided key (adversarial test
    below), and every pair compared 13,928 on the real data. So the effect is only that the pair's
    own count understates.
  - **Fix (optional):** fail when a pair's `compared` differs from the season's team-game count.
- **The `[opponent]` marker is accepted on any catalog** (`inventory.py:310`).
  - It is accepted on `ratings[opponent]:`, `strength[opponent]:` and `dataset[opponent]:`. The
    docs say it belongs only "after a per-team-game catalog".
  - Nothing uses it wrongly today.
  - **Fix:** allow it only for the team-game catalogs (`box_score`, `team_game`, `team_stats`).
- **Rounding to 9 decimals does not make the sum independent of the order it is added in**
  (`parity_rules.py:214-215`).
  - Sums that differ by one unit in the last place can fall on either side of a rounding
    midpoint. `[0.1000000005, 1.0, -1.0]` sums to `0.1` in one order and `0.100000001` in the
    other.
  - It is stable on the real data, as shown at 4 and 8 threads.
  - **Fix:** sum in a fixed order, for example `math.fsum(series.to_list())`, which is exactly
    rounded and order-independent. Keep the rounding for display.
